Dynamic OG Images in Next.js Without Writing Satori JSX

Satori works, but it makes you pay for it. Font loading, CSS subset surprises, JSX for a static image, edge runtime constraints — there is a simpler path. Here is the full tutorial.

The Satori Problem

next/og ships with Satori under the hood. The idea is elegant: write JSX, get a PNG. In practice, four friction points slow you down before your first image renders.

1. Font loading on every request

Satori cannot read font files from disk — the edge runtime has no fs access. So the recommended pattern is fetching your font as an ArrayBuffer on every request:

app/api/og/route.tsx
export const runtime = 'edge'

export async function GET(req: Request) {
  // Fetched fresh on EVERY request — adds ~80-120ms cold
  const fontData = await fetch(
    new URL('../../../assets/Inter-Bold.ttf', import.meta.url)
  ).then((r) => r.arrayBuffer())

  return new ImageResponse(
    <div style={{ fontFamily: 'Inter' }}>...</div>,
    { fonts: [{ name: 'Inter', data: fontData, weight: 700 }] }
  )
}
Warning

Even with Vercel Edge caching, the font fetch fires on cache misses and cold starts. Two custom fonts means two round trips before rendering begins.

2. The CSS subset that bites you mid-project

Satori does not implement full CSS. It uses a custom layout engine. The unsupported properties are not always obvious until you hit them in production:

Things that silently fail or error in Satori
// No CSS Grid — use flexbox only
style={{ display: 'grid', gridTemplateColumns: '1fr 1fr' }}  // ignored

// No mixed-unit calc()
style={{ width: 'calc(100% - 48px)' }}  // broken

// No multiline text-overflow
style={{ display: '-webkit-box', WebkitLineClamp: 3 }}  // ignored

// No background-clip: text
style={{ backgroundClip: 'text', WebkitBackgroundClip: 'text' }}  // noop

3. JSX for a static image is the wrong abstraction

A 1200x630 PNG has no state. It does not re-render. It never handles a click event. Writing it as a React component — with camelCase inline styles, JSX fragments, and import.meta.url tricks — is cognitive overhead solving a problem that does not need React:

The boilerplate you write before any actual design work
import { ImageResponse } from 'next/og'

export const runtime = 'edge'
export const contentType = 'image/png'
export const size = { width: 1200, height: 630 }

export default async function Image({ params }: { params: { slug: string } }) {
  const post = await getPost(params.slug)  // can't use Prisma here
  const font = await fetch('https://...').then(r => r.arrayBuffer())
  return new ImageResponse(
    <div style={{ display: 'flex', flexDirection: 'column', ... }}>
      <h1 style={{ fontSize: 48, fontWeight: 800, ... }}>{post.title}</h1>
    </div>,
    { width: 1200, height: 630, fonts: [{ name: 'Inter', data: font }] }
  )
}

4. Edge runtime conflicts with Node API routes

next/og requires export const runtime = 'edge'. But your data-fetching API routes — the ones using Prisma, fs, or native Node modules — must run on the Node runtime. You cannot mix runtimes in one route file. This forces you to split your OG image into a separate route just to satisfy the runtime constraint, or proxy through a Node route, or give up and use a third-party service anyway.

The URL-Params Approach

Instead of rendering images in your own runtime, you call an API that already handles rendering, caching, fonts, and CDN delivery. You pass parameters in the URL. You get a PNG back.

A real SnapOG URL looks like this:

https://api.snapog.dev/og?title=My+Post+Title&subtitle=by+Alok&theme=dark

That returns a 1200×630 PNG. No font loading. No JSX. No edge runtime declaration. Just a URL you drop into <meta property="og:image">.

2

Create lib/og.ts

Build a typed utility that constructs the SnapOG URL from params. Keep it simple — it is just a URL builder:

lib/og.ts
const SNAPOG_BASE = 'https://api.snapog.dev/og'
const API_KEY = process.env.SNAPOG_API_KEY!

interface OGParams {
  title: string
  subtitle?: string
  theme?: 'dark' | 'light'
  logo?: string   // URL to your logo image
  tag?: string    // top-left label e.g. "Tutorial"
}

export function ogUrl(params: OGParams): string {
  const url = new URL(SNAPOG_BASE)
  url.searchParams.set('key', API_KEY)
  url.searchParams.set('title', params.title)
  if (params.subtitle) url.searchParams.set('subtitle', params.subtitle)
  if (params.theme)    url.searchParams.set('theme', params.theme)
  if (params.logo)     url.searchParams.set('logo', params.logo)
  if (params.tag)      url.searchParams.set('tag', params.tag)
  return url.toString()
}

Add your key to .env.local: SNAPOG_API_KEY=sk_live_xxxx

3

Use in generateMetadata (App Router)

Call ogUrl() inside your generateMetadata export. No API route needed. No edge runtime. No font fetching:

app/blog/[slug]/page.tsx
import { ogUrl } from '@/lib/og'
import { getPost } from '@/lib/db'  // Prisma, fs, anything — Node runtime
import type { Metadata } from 'next'

export async function generateMetadata(
  { params }: { params: { slug: string } }
): Promise<Metadata> {
  const post = await getPost(params.slug)

  return {
    title: post.title,
    openGraph: {
      images: [
        {
          url: ogUrl({
            title: post.title,
            subtitle: `by ${post.author} · ${post.readTime} min read`,
            theme: 'dark',
            tag: post.category,
          }),
          width: 1200,
          height: 630,
          alt: post.title,
        },
      ],
    },
    twitter: { card: 'summary_large_image' },
  }
}
4

Verify it works

Copy the generated URL from your browser DevTools (inspect the og:image meta tag). Paste it directly into a new browser tab — you should see the 1200×630 PNG. Then validate the full card at Twitter Card Validator and Facebook Debugger.

Dynamic OG for Different Page Types

The same ogUrl() utility handles every page type. Different params, different image:

lib/og-presets.ts — four patterns in one file
import { ogUrl } from './og'

// Blog post
export const blogOG = (title: string, author: string, category: string) =>
  ogUrl({ title, subtitle: `by ${author}`, tag: category, theme: 'dark' })

// Product / e-commerce page
export const productOG = (name: string, price: string, logoUrl: string) =>
  ogUrl({ title: name, subtitle: `Starting at ${price}`, logo: logoUrl, theme: 'light' })

// User profile page
export const profileOG = (displayName: string, bio: string, avatar: string) =>
  ogUrl({ title: displayName, subtitle: bio, logo: avatar, theme: 'dark' })

// Docs / reference page

Pages Router Pattern

Nothing changes conceptually. Build the URL, put it in the Head component:

pages/blog/[slug].tsx — Pages Router
import Head from 'next/head'
import { ogUrl } from '@/lib/og'
import { getPost } from '@/lib/db'
import type { GetServerSideProps } from 'next'

export const getServerSideProps: GetServerSideProps = async ({ params }) => {
  const post = await getPost(params?.slug as string)
  return { props: { post } }
}

export default function BlogPost({ post }) {
  const imageUrl = ogUrl({ title: post.title, subtitle: post.author, theme: 'dark' })

  return (
    <>
      <Head>
        <meta property="og:image" content={imageUrl} />
        <meta name="twitter:card" content="summary_large_image" />
        <meta name="twitter:image" content={imageUrl} />
      </Head>
      {/* page content */}
    </>
  )
}

Performance

Performance note

SnapOG renders each unique URL once and caches the PNG at the CDN edge. Subsequent requests for the same URL are served in under 20ms globally — faster than most self-hosted Satori setups which render on every cold start. Cache-Control headers set a 30-day TTL. Crawlers never wait on your server.

Summary

  • No new API route needed. The OG URL is built at the generateMetadata level — it is just a string computed server-side, never a separate endpoint you have to maintain.
  • No runtime constraints. You can use Prisma, fs, Redis, or any Node-only library in the same route file. The OG image is decoupled.
  • No font management. Fonts are pre-loaded on SnapOG's infrastructure. You pick a theme, it handles typography.
  • Iteration is instant. Changing the OG image means changing a string. Test it by pasting the URL in a browser tab. No redeploy, no rebuild, no waiting.
